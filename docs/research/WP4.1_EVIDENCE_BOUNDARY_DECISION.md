# WP4.1 Evidence Boundary Decision

## Summary of Findings

WP4 showed zero evaluated functions across 9 cases due to:

- p-limit: JS source (TS-only analyzer correctly returned 0, but selection was wrong)
- zod/zustand: coverage command failure became analyzer failure, masking as PASS/COMPLETE

Track A: crap-typescript obtains boundaries and CC via TypeScript Compiler API (parser.js), and coverage via Istanbul JSON (coverage-final.json) generated by running vitest/jest. It can reuse existing artifact if present, but otherwise runs coverage command and throws on non-zero exit, causing total failure rather than partial unknown.

Track B: External coverage artifacts (Istanbul JSON) contain statement/branch spans that can be mapped to function ranges via integer interval overlap without TS parsing. LCOV is line-only, insufficient for precise function mapping without parser.

Track C: Composition via independent providers is viable: core parser (crap-typescript-core's parseFileMethods) for CC+range without test execution, plus external Istanbul JSON for coverage, plus tiny CRAP arithmetic (CC^2*(1-cov)^3+CC). This is not custom analysis per governing principle.

## Decision Criteria

- Smallest reliable deterministic boundary?
- Preserves "consumes analysis" principle?
- Avoids becoming responsible for every project's test environment?
- Portable without target install?
- Failure semantics correct?

## Options Evaluated

### RETAIN CURRENT PROVIDER
Keep `npx --no-install crap-typescript` as is.
- Pros: No code change, already proven on fixture.
- Cons: Requires target to have package installed, owns test execution (coverage command), fails on many real repos (6/9 WP4), cannot distinguishJS vs TS, fragile package manager detection. Not portable.

### ADAPT PROVIDER BOUNDARY
Keep crap-typescript but adapt invocation and configuration:
- Use `npx --yes @barney-media/crap-typescript@0.5.0` (pinned, no target install)
- Prefer existing coverage artifact if present (`coverage/coverage-final.json`), avoid running coverage command when artifact exists (already supported)
- Possibly add flag to allow coverage-unavailable as unknown rather than failure (would require upstream or local patch)

Pros: Minimal change, reuses proven parser+CC, improves portability somewhat.
Cons: Still owns test execution when artifact absent, still fails on coverage command for many repos, still requires handling JS vs TS.

### COMPOSE EXISTING PROVIDERS
Compose:
```
Git -> changed intervals
crap-typescript-core parser (standalone) -> function range + CC
existing coverage artifact (Istanbul JSON) -> coverage
tiny deterministic arithmetic -> CRAP
```
- Git: existing `git diff -U0` (proven)
- CC provider: `crap-typescript-core`'s `parseFileMethods` + CC calculation (mature, deterministic, machine-readable, no test execution, Apache-2.0, already transitive dep)
- Coverage: read existing `coverage/coverage-final.json` if project generates it via its own `npm run coverage`; do not generate it. If absent, mark coverage null → NOT_EVALUATED.
- CRAP: pure function, not analyzer.

Pros: Does not own test execution, does not require target install if core is bundled or invoked via `npx --yes` with pinned version, more portable, handles JS vs TS via file selection, failure semantics can be correct (missing artifact → unknown, not failure).
Cons: Requires wiring attribution (statement→method overlap) which is tiny deterministic math, not AST; need to maintain composition.

### STOP
Stop project: evidence acquisition is too hard to be small.
- Pros: Acknowledges WP4 failures.
- Cons: Earlier verified work (correlation, envelope, 0 vs null, rule logic) remains valid; composing existing providers is still small and deterministic, so STOP is premature.

## Decision

**COMPOSE EXISTING PROVIDERS**

Rationale:

- WP4's core issue is evidence acquisition owning test execution and requiring target install. Composing existing providers removes test execution ownership and, if bundled, removes install requirement.
- Track B shows external artifacts are standard and mappable without parsing.
- Track C shows a mature independent CC provider already exists as part of current dependency (core), so no new unproven analyzer.
- Tiny CRAP arithmetic is explicitly allowed as not being source analysis.
- This is the smallest reliable deterministic boundary that keeps the project as a consumer, not a test orchestrator.
- Failure semantics can then be correct: missing artifact → unknown (NOT_EVALUATED, INCOMPLETE) not FAILED; only true provider execution failure (e.g., parse error) → FAILED.

## What This Means

Next implementation step should:

- Bundle or pin `crap-typescript-core` parser for CC+range without coverage command
- Read existing `coverage/coverage-final.json` if present, otherwise coverage null
- Compute CRAP via tiny arithmetic
- Keep Git correlation and envelope
- Implement failure semantics decision (analysisStatus/gate/completeness separation)

Do not implement baseline/delta, test/lint/security evidence, multi-language support.

## Final Decision

COMPOSE EXISTING PROVIDERS
