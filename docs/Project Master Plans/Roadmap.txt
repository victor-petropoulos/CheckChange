PURPOSE

This document is a forward execution plan for the remaining Code-Risk / CRAP research project. It is intentionally provisional. It is designed to give another LLM, including OpenCode and the coding LLM used within OpenCode, enough context to execute the remaining work without losing the experimental discipline established through WP4R and WP5.

This document must not be interpreted as authorization to implement all future capabilities described here immediately.

The implementing LLM must continuously distinguish between:

- what has already been proven;
- what is currently being tested;
- what is planned;
- what is assumed;
- what is hypothesized;
- what is a possible future direction.

A future work package must not be treated as authorized until the preceding work package's exit gate has been satisfied.

The governing principle for the remainder of the project is:

EVIDENCE DETERMINES THE NEXT STEP. THE ROADMAP DOES NOT OVERRIDE EVIDENCE.

At the beginning of every work package, the implementing LLM must:

1. Inspect the actual repository.
2. Inspect the current source.
3. Inspect the current tests.
4. Inspect the current documentation.
5. Read the completed prior work-package results.
6. Establish the actual current behavior.
7. Compare that behavior with this provisional roadmap.
8. Identify assumptions that are no longer true.
9. Identify any contradictions between the roadmap and the actual repository.
10. Adjust the provisional plan when the evidence justifies doing so.
11. State what it intends to do before making broad changes.

At the end of every work package, the implementing LLM must:

1. Report what was actually done.
2. Report what was actually observed.
3. Distinguish failures caused by the current work from pre-existing failures.
4. Record newly discovered findings.
5. Record limitations.
6. Record unresolved questions.
7. Determine whether the exit gate passed.
8. Stop at the gate unless explicit authorization exists to continue.

The project should not optimize for code volume.

The objective is a defensible deterministic evidence system and a defensible research conclusion.


PROJECT PURPOSE AND CORE THESIS

The project is a deliberately small deterministic changed-function code-risk / CRAP prototype.

The core conceptual pipeline is:

Git change
    ↓
Changed functions
    ↓
Complexity evidence
    +
Coverage evidence
    ↓
Deterministic attribution
    ↓
CRAP calculation
    ↓
Threshold evaluation
    ↓
Structured risk evidence

The critical architectural distinction is between EVIDENCE and JUDGMENT.

The deterministic pipeline should establish factual evidence such as:

- which functions changed;
- what their complexity is;
- what their measured coverage is;
- whether coverage was actually available;
- what CRAP value follows from those measurements;
- what threshold was applied;
- whether evaluation completed successfully;
- what provenance exists for the measurements.

A human or LLM may then reason about what that evidence means.

The LLM should not invent measurements that the deterministic pipeline is responsible for producing.

The potential long-term relationship with Engram remains a hypothesis. A future implementation may eventually use the deterministic evidence engine as an evidence layer for AI-assisted code review, but the research project must not distort its methodology merely because that outcome is strategically attractive.


PROJECT HISTORY THAT MUST BE PRESERVED

The project previously went through WP4R, including the final verification and freeze work.

The deterministic prototype uses:

- Git changed-function information;
- TypeScript complexity analysis;
- crap-typescript-core;
- Istanbul-compatible coverage JSON;
- deterministic coverage attribution;
- deterministic CRAP calculation;
- defined thresholds;
- explicit statuses;
- structured output.

The project deliberately excludes autonomous LLM classification from the deterministic evidence/rule pipeline.

The caller or CI environment supplies evidence.

The prototype consumes that evidence.

This boundary is important and should remain intact unless a future work package explicitly demonstrates that changing it is justified.


WP4R FOUNDATION

WP4R established the deterministic foundation.

Important principles coming out of WP4R include:

- coverage 0 is a valid measurement;
- unavailable coverage must remain distinguishable from zero;
- Git-derived intervals must be real rather than fabricated;
- statuses such as SUCCESS, WARN, and INCOMPLETE must correspond to actual conditions;
- high complexity plus zero coverage must produce a real CRAP value rather than being converted into an unavailable state;
- external Istanbul-compatible coverage may be supplied explicitly;
- the prototype should not autonomously classify changes using an LLM;
- the caller/CI generates evidence and the deterministic engine consumes it.

These are not merely historical details.

They are regression invariants.

WP5.4 FINDINGS AND CURRENT POSITION

WP5.4 identified four semantic, status, and diagnostic truthfulness findings.

FM-V01 — Coverage capability mislabel

The system can incorrectly communicate that coverage capability is available when the requested/default coverage source is not actually available.

The important distinction is:

coverage capability exists

versus:

coverage evidence was actually obtained.

The second is what matters to a particular analysis.

The implementation must not claim evidence exists merely because a coverage mechanism or analyzer capability exists.


FM-D10 — Git ENOENT misclassification

When the Git executable is unavailable, the resulting error can be incorrectly described as:

"Not a git repository"

That is factually wrong.

The correct distinction is:

Git executable unavailable

versus:

Git executable available, but target is not a repository.

These are different environmental conditions and must remain distinguishable.


FM-G06 — Missing coverage reported as malformed

A missing coverage file and a malformed coverage file are different conditions.

They must remain distinct.

MISSING means:

The requested artifact does not exist.

MALFORMED means:

The artifact exists but cannot be parsed or validated.

The distinction matters because the remedies are different.

A missing file may mean coverage was never generated or the path is wrong.

A malformed file means coverage was generated or supplied but the artifact is invalid or unsupported.


FM-G07 — Composed-path analyzerStatus hardcoded

A composed-path analyzer result can incorrectly report:

"passed"

without demonstrating that analysis actually completed successfully.

The status must describe actual execution and evaluation state.

The fact that an object was returned is not sufficient evidence that analysis passed.


PERMANENT SEMANTIC INVARIANTS

The following distinctions must be treated as project-wide invariants.


ZERO IS NOT NULL

coverage = 0

means:

A valid measurement exists and measured coverage is zero.

coverage = null, or equivalent unavailable state,

means:

A valid measurement was not obtained.

Example:

complexity = 25
coverage = 0
CRAP = valid calculated value

must not become:

coverage unavailable
CRAP unavailable

simply because coverage is zero.


MISSING IS NOT MALFORMED

Example:

coverage.json does not exist

is not equivalent to:

coverage.json exists but contains invalid JSON.

The distinction must survive from the evidence acquisition layer through the final output.


GIT UNAVAILABLE IS NOT NOT-A-REPOSITORY

Example:

git: command not found

is an environment/tooling failure.

Example:

fatal: not a git repository

is a repository-state failure.

They must not collapse into one diagnostic.


ANALYSIS SUCCESS MUST MEAN SUCCESSFUL ANALYSIS

An object being returned is not evidence that analysis succeeded.

For example:

{
  "analyzerStatus": "passed",
  "result": null
}

is not inherently a successful analysis.

The status must correspond to the actual evaluation path.


EVIDENCE, POLICY, AND DECISION ARE DIFFERENT

Evidence:

complexity = 18
coverage = 0
CRAP = 324

Policy:

CRAP > 30

Decision:

additional human review recommended

These are three different layers.

The engine should not unnecessarily combine them.

WP5.6 COVERAGE STRATEGY

For a large repository such as apollo-client, running the full test suite for every historical case may be unnecessarily expensive.

The planned strategy is a two-tier approach.

TIER 1:

Run at least one representative case through the full suite where practical.

Purpose:

Validate the general coverage methodology against the repository.

TIER 2:

Use case-attributable or appropriately scoped coverage for remaining cases where appropriate.

The scope must be explicitly documented.

Never claim:

"full-suite coverage"

when only:

"scoped coverage"

was used.

WP5.6 EXAMPLE CASE OUTCOMES

OUTCOME A — HIGH CRAP IDENTIFIES AN OBVIOUSLY RISKY CHANGE

OUTCOME B — HIGH CRAP BUT OBVIOUSLY HARMLESS CHANGE

Do not immediately change the formula.

- whether the function is inherently complex but stable;

OUTCOME C — LOW CRAP BUT REVIEWER IDENTIFIES SERIOUS RISK

Possible missing context:

- architectural centrality;
- data sensitivity;
- historical defect patterns.

These are hypotheses.

Do not immediately add them to the engine.

OUTCOME D — COVERAGE UNAVAILABLE

This is not automatically a failed case.

Truthfulness may itself be a successful result.

WP5.6 CLAIMS/EVIDENCE MATRIX

Create a matrix conceptually like:

Claim | Evidence | Confidence | Limitation

Changed functions can be identified | historical cases | Medium/High | repository-specific

CRAP is deterministic | repeated runs | High | tested environments

Output is explainable | human review | Medium | limited sample

The confidence must match the actual sample.

First establish a baseline.


WP7 OBSERVABILITY

Operational diagnostics should explain:

- what was attempted;
- which evidence sources were used;
- what succeeded;
- what failed;
- why;
- whether the result is complete.

Operational diagnostics must not contradict analytical status.


WP7 RELEASE READINESS

Before calling the system production-ready:

- clean install;
- reproducible build;
- regression suite;
- integration tests;
- security review;
- performance baseline;
- documentation;
- failure recovery;
- compatibility checks.

A release candidate should be reproducible by someone other than the original implementer.


WP7 POSSIBLE OUTCOMES

OUTCOME A — PRODUCTIONIZATION SUCCEEDS

Proceed to WP8.


OUTCOME B — PERFORMANCE UNACCEPTABLE

Return to targeted optimization.


OUTCOME C — INTEGRATION TOO FRAGILE

Reconsider architecture.


OUTCOME D — OPERATIONAL COMPLEXITY OVERWHELMS VALUE

Potentially stop or narrow the product.


OUTCOME E — EVIDENCE CONTRACT PROVES UNSTABLE

Return to WP6 rather than freezing an unstable contract.


WP8 — REAL-WORLD VALIDATION

OBJECTIVE

Determine whether the productionized capability works and provides value outside the controlled WP5 experiment.

WP8 is where assumptions meet broader reality.


WP8 REPOSITORY DIVERSITY

Where practical, include repositories differing in:

- size;
- architecture;
- test strategy;
- monorepo structure;
- coverage tooling;
- development style;
- supported languages.

The objective is not statistical proof.

It is boundary discovery.


WP8 REAL CHANGE VALIDATION

Evaluate actual historical or permitted engineering changes.

For each:

change
 ↓
identified functions
 ↓
complexity
 ↓
coverage
 ↓
CRAP
 ↓
risk evidence
 ↓
reviewer interpretation
 ↓
actual/expected engineering significance

The important question becomes:

Does the evidence correspond reasonably well with engineering reality?


WP8 FALSE POSITIVES

A false-positive-like case might look like:

high CRAP

but:

reviewer: low practical concern

Do not immediately conclude the metric is wrong.

Investigate:

- complexity is high by design;
- coverage measurement is incomplete;
- generated code;
- stable but complex utility;
- threshold too aggressive;
- missing context.

Possible conclusion:

"CRAP is a useful attention signal but not a standalone risk classifier."

That may be more accurate than changing the formula.


WP8 FALSE NEGATIVES

A more concerning case may be:

low CRAP

but:

reviewer: significant risk

Ask what the current evidence model cannot see.

Potential missing dimensions:

- dependency blast radius;
- security sensitivity;
- public API exposure;
- architecture;
- data sensitivity;
- historical defect rate;
- concurrency;
- external integration.

Again, these are hypotheses.

Do not automatically add them.


WP8 DEVELOPER EXPERIENCE

Evaluate:

- trust;
- comprehension;
- noise;
- friction;
- review focus;
- willingness to use;
- whether results are actionable.

A technically correct result that engineers ignore is not necessarily a successful product.


WP8 AI-GENERATED CODE

If Engram is involved, compare changes based on their evidence rather than assuming authorship determines risk.

The engine should evaluate:

what changed
+
how complex it is
+
how well it is tested

not:

who or what generated it

unless future evidence proves authorship is itself relevant to a specific risk model.


WP8 DECISION FORKS

IF RELIABILITY IS WEAK:

Return to WP7.


IF RELIABILITY IS STRONG BUT USEFULNESS IS WEAK:

Investigate signal quality.


IF USEFULNESS IS STRONG:

Expand validation.


IF FALSE POSITIVES DOMINATE:

Investigate:

- thresholds;
- evidence completeness;
- policy;
- CRAP limitations.


IF FALSE NEGATIVES DOMINATE:

Investigate missing evidence dimensions.


IF OPERATIONAL COST IS TOO HIGH:

Optimize or narrow the use case.


WP8 EXIT ARTIFACTS

Produce:

- real-world validation report;
- false-positive analysis;
- false-negative analysis;
- operational findings;
- developer-experience findings;
- adoption assessment;
- limitations;
- recommended next steps.

The recommended next step must be evidence-backed.

This might reveal:

Therefore history must be validated before becoming a product feature.

Potential future evidence:

This could potentially be more useful than:

current CRAP = 42

because it describes change in risk.

But it should not be assumed to be better.

WP8 evidence should determine whether this is worth pursuing.

MASTER LIST OF QUESTIONS TO ASK AT EVERY WORK PACKAGE

Before implementation:

1. What are we trying to prove?
2. What is already known?
3. What is only assumed?
4. What evidence would falsify the assumption?
5. What is the smallest experiment?
6. What is explicitly out of scope?
7. What is the exit gate?

During implementation:

1. Did the actual repository match expectations?
2. Did we discover an existing capability?
3. Did we discover a contradiction?
4. Did we change public behavior?
5. Did we change semantics?
6. Did we introduce nondeterminism?
7. Did we accidentally expand scope?

After implementation:

1. What changed?
2. What did we prove?

6. Did the gate pass?
7. What does the evidence imply for the next work package?


REQUIRED TREATMENT OF PROVISIONAL ASSUMPTIONS

Every future assumption should be mentally labeled:

ASSUMED

until demonstrated.

Examples:

"CRAP is useful to reviewers"

is assumed until WP5.6/WP8 evidence supports it.

"Engram is the best consumer"

is assumed until WP6 evidence supports it.

"Historical CRAP delta will be useful"

is assumed until validated.

"Additional languages are worth supporting"

is assumed until demand and evidence support it.

This prevents the roadmap from turning hypotheses into requirements.


WHAT A STRONG RESULT LOOKS LIKE

A strong result is not necessarily:

more features.

A strong result may be:

We tested X.

We observed Y.

Therefore we can confidently claim Z.

However, limitation Q remains.

For example:

"Changed-function risk evidence was reproducible across the tested TypeScript repositories. Coverage attribution worked under the tested Istanbul-compatible configurations. Reviewers found high-complexity/low-coverage changes useful as attention signals. However, the sample was small and the signal does not capture dependency or architectural risk."

That is a stronger engineering conclusion than:

"The system detects risky code."

The first is evidence-backed and scoped.


WHAT A NEGATIVE RESULT MEANS

The project is allowed to conclude:

- CRAP is not sufficiently useful by itself;
- coverage attribution is unreliable in important environments;
- the signal is too noisy;
- reviewers do not trust it;
- the cost of obtaining coverage outweighs the value;
- a deterministic evidence layer is useful but CRAP alone is insufficient;
- the best application is narrower than originally expected.

A negative result is preferable to unsupported product claims.


WHAT A POSITIVE RESULT MEANS

Even if results are strong, do not immediately expand scope.

Instead:

1. document the result;
2. identify why it worked;
3. identify the boundary conditions;
4. reproduce it;
5. validate the generalization;
6. then expand.

Unexpected success should increase rigor.

          |             |             |

               NORMALIZED EVIDENCE

              DETERMINISTIC ENGINE
                        |

          |             |             |
        CRAP          Status      Provenance
          |             |             |
          +-------------+-------------+

                        |

              |                   |
             CI                 ENGRAM

The most important boundary is:

Evidence Engine
      ↓
Factual deterministic output
      ↓
Consumer / LLM

The consumer should not have to reconstruct the evidence.


WHY THE DETERMINISTIC BOUNDARY MATTERS

An LLM can say:

"This change looks risky."

That is subjective.

A deterministic engine can say:

changed function:
calculateEligibility()

complexity:
21

coverage:
0%

CRAP:
441

threshold:
30

analysis:
successful

A reviewer or LLM can then reason:

"This changed function is highly complex and has zero measured test coverage. The evidence warrants additional review."

The LLM is now reasoning from evidence rather than fabricating evidence.

This is potentially one of the strongest long-term ideas in the project.

It must nevertheless be earned through validation.


POTENTIAL RISKS THROUGH WP5.4–WP9

RISK 1 — SCOPE EXPLOSION

The project gradually becomes a general code-quality platform.

Response:

Return to the evidence engine's core purpose.


RISK 2 — CRAP BECOMES TREATED AS UNIVERSAL RISK

CRAP measures a specific combination of complexity and coverage.

It does not automatically measure:

- architecture;
- security;
- dependency blast radius;
- business criticality;
- maintainability in every dimension.

Response:

Describe it as a signal, not universal truth.


RISK 3 — LLM JUDGMENT LEAKS INTO DETERMINISTIC EVIDENCE

Response:

Maintain strict evidence/judgment boundary.


RISK 4 — COVERAGE QUALITY IS MISTAKEN FOR COVERAGE AVAILABILITY

Response:

Preserve provenance and validity states.


RISK 5 — FALSE PRECISION

A CRAP score may look more authoritative than the underlying evidence warrants.

Response:

Maintain context and provenance.


RISK 6 — THRESHOLD BECOMES THE PRODUCT

Thresholds are policy.

The evidence engine should remain independent.


RISK 7 — EXPERIMENTAL RESULTS BECOME PRODUCT CLAIMS

A handful of repositories cannot establish universal reliability.

Response:

Scope every claim.

Finding | Likely Direction | What Not To Do

Strong usefulness, simple integration | CI/CLI | Build platform prematurely

Strong usefulness, AI workflow benefit | Engram | Put LLM in evidence pipeline

Strong evidence, unclear consumer | Evidence API | Build multiple consumers

Weak usefulness | Narrow/research/stop | Productize anyway

Strong signal but missing context | Evidence expansion | Immediately rewrite CRAP

Language limitation dominant | Adapter research | Build every language

Historical trend clearly valuable | Baseline/history | Build large data platform first

Operational cost high | Optimization/narrowing | Hide runtime cost

High false negatives | Missing-evidence research | Claim comprehensive risk detection


FINAL SUCCESS CRITERIA FOR THE OVERALL PROJECT

The project should ultimately be able to defend some or all of these statements:

1. Changed functions can be identified deterministically under defined conditions.
2. Complexity can be measured deterministically.
3. Coverage can be attributed deterministically under defined conditions.
4. CRAP can be calculated deterministically.
5. Zero coverage is handled correctly.
6. Missing and malformed evidence are distinguished.
7. Git/environment failures are represented truthfully.
8. Status propagation is semantically correct.
9. Results are reproducible.
10. Evidence has sufficient provenance to explain where it came from.
11. The signal is useful enough for at least one clearly defined engineering use case.
12. The system's limitations are understood.
13. The boundary between deterministic evidence and LLM/human judgment is explicit.
14. Any proposed future expansion is supported by evidence.

The project does NOT need to prove:

- every programming language;
- every coverage provider;
- every repository architecture;
- universal software risk prediction;
- that CRAP is the best possible risk metric.

FINAL OPERATING RULE

When uncertain:

STOP
 ↓
INSPECT
 ↓
MEASURE
 ↓
DOCUMENT
 ↓
CLASSIFY
 ↓
DECIDE

Do not guess.

Do not silently broaden scope.

Do not silently change methodology.

Do not treat provisional architecture as final.

Do not treat hypotheses as findings.

Do not let an LLM replace deterministic evidence.

Do not let future product ambitions dictate current experimental conclusions.

The purpose of this roadmap is not to guarantee that WP9 looks a particular way.

The purpose is to ensure that every step from WP5.4 through WP9 is justified by what the project actually learns.

The strongest possible end state is not necessarily a large product.

It is a defensible engineering system and a defensible body of evidence showing:

WHAT THE SYSTEM KNOWS

+

WHAT THE SYSTEM DOES NOT KNOW

+

HOW RELIABLE THE EVIDENCE IS

+

HOW THAT EVIDENCE CAN BE USED

If that foundation proves valuable, then the project has a credible basis for potentially becoming:

- a deterministic CI risk gate;
- an engineering review signal;
- an Engram evidence layer;
- a broader code-risk evidence platform.

Those are potential outcomes.

They must remain outcomes of the evidence, not assumptions built into the experiment.
