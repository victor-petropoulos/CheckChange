# WP12 Measurement Specification

This document defines the measurement criteria for evaluating the CI integration validation experiment (WP12) against the Roadmap S7 goals.

## Measurement Rubric

| Category | Measurable Criteria | Pass/Fail Thresholds | Linkage to Invariants |
|----------|---------------------|----------------------|------------------------|
| **Setup Complexity** | - Number of steps in pipeline definition (excluding setup actions)<br>- Lines of configuration in workflow YAML (excluding comments and blank lines) | - Steps ≤ 5 (excluding setup actions)<br>- Config lines ≤ 50 per workflow | INV-01: CI must be minimally invasive and easy to adopt |
| **Failure Modes** | - Exit code behavior for: <br>  • Missing coverage file<br>  • Malformed JSON output<br>  • Base ref unresolvable (e.g., nonexistent commit)<br>  • Git executable not found (ENOENT)<br>  • --crap-threshold override not propagating to policy/ruleResults | - Missing coverage: exit code 1 (FAILED)<br>- Malformed JSON: exit code 1 (FAILED)<br>- Base ref unresolvable: exit code 1 (FAILED) with specific error message<br>- Git ENOENT: exit code 1 (FAILED) with specific error message<br>- Threshold override: policy.crapThreshold and ruleResults[0].threshold reflect overridden value | INV-02: CI must fail fast and with actionable errors on invalid inputs<br>INV-03: Configuration overrides must propagate to engine policy and rule results |
| **Evidence Completeness** | - Presence of all schema v0.2 fields in generated JSON:<br>  • schemaVersion, analysis {base, target}, capabilities, changedFunctions, ruleResults, policy, analysisStatus, gate, completeness<br>  • Provenance fields: capabilities (git, complexity, coverageArtifact) | - All required schema v0.2 fields present<br>- capabilities.git, capabilities.complexity, capabilities.coverageArtifact must be present (values may be absent/not applicable) | INV-01: CI must produce a complete, schema-compliant evidence artifact |
| **Developer Comprehension** | - Time-to-first-success: minutes from cloning repo to successful pipeline run on local machine (dry-run harness)<br>- Cognitive load: subjective rating (1-5) based on number of concepts a contributor must grasp to modify pipelines | - Time-to-first-success ≤ 10 minutes (assuming Node 24 and git available)<br>- Cognitive load ≤ 3 (simple YAML with minimal custom scripting) | INV-04: CI must be understandable and maintainable by average contributor |
| **CI Cost** | - Wall-clock time for each pipeline stage:<br>  • Setup (actions/checkout, actions/setup-node, npm ci)<br>  • Build (npm run build)<br>  • Test (vitest run --coverage)<br>  • Evidence generation (node dist/cli.js check ...)<br>  • Artifact upload (actions/upload-artifact) | - Total pipeline wall-clock ≤ 5 minutes on standard GitHub-hosted ubuntu-latest runner<br>- Each stage individually ≤ 2 minutes (except test stage which may be higher due to vitest) | INV-01: CI must be fast and economical to run |
| **Reproducibility** | - JSON equivalence (ignoring timestamps and ephemeral fields) when running the same pipeline twice with identical inputs (same base ref, same coverage) | - Two consecutive runs produce JSON that is equivalent after removing: <br>  • analysis.base (if it's a timestamp-based ref)<br>  • Any fields representing runtime timestamps<br>  • Any fields representing ephemeral resource IDs | INV-01: CI must produce deterministic evidence given identical inputs (per WP5 determinism invariants) |
| **Path Handling** | - Correctness of F-03 normalizeCoveragePaths rebasing:<br>  • When coverage file is generated in a subdirectory, the engine must rebase paths to be relative to the repo root<br>  • Verified by checking that file paths in coverage artifact (if present) or in engine output are repo-relative | - All file paths in engine output (if any) or in referenced coverage artifact are repo-relative (no absolute paths, no leading '../' outside repo)<br>- When base ref is changed, the engine correctly rebases coverage paths to the target commit's file structure | F-03: normalizeCoveragePaths must rebase coverage paths to the target commit's file structure |
| **Artifact Handling** | - Default artifact: size and retention of automatically uploaded coverage/coverage-final.json<br>- Explicit artifact: behavior when --coverage-file points to a custom location<br>- Retention: artifact availability in GitHub UI after workflow completion | - Default artifact size ≤ 10MB (for typical projects)<br>- Explicit artifact: engine must read from specified path and produce same JSON structure<br>- Artifacts retained for at least 90 days (GitHub default) or as specified in workflow | INV-01: CI must handle coverage artifacts robustly regardless of location or size (within reason) |
| **Config Burden** | - Propagation of --crap-threshold override:<br>  • Check that policy.crapThreshold in JSON matches the overridden value<br>  • Check that ruleResults[0].threshold (if present) matches the overridden value<br>  • Verify that default threshold (30) is used when no override is given | - Override value must exactly match provided --crap-threshold argument<br>- Default threshold must be 30 when no override is present<br>- Threshold must be a positive integer | INV-03: Configuration overrides must propagate to engine policy and rule results<br>INV-01: CI must use sensible defaults (crapThreshold=30) |

## Notes

- All measurements are to be taken using the dry-run harness documented in LOCAL_DRYRUN.md for local validation, and/or via GitHub Actions for cloud validation.
- Where subjective measures are noted (e.g., cognitive load), a simple survey of developers familiar with the project but not the WP12 changes shall be conducted.
- Thresholds are based on project-specific norms and may be adjusted based on baseline measurements from WP11.
